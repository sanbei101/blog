# 技术博客写作规范

本规范旨在写出真正高水平工程师的博客质感:**语言极其简单简练,毫无说教感,把所有复杂度留给代码、数据和架构设计**。

---

## 一、三条铁律

### 1. 绝对不要在名词后面跟括号英文解释
* ❌ 严禁出现类似写法:形式化建模(Problem Formalization)、基准(Ground Truth)、对拍(Stress Testing)、有向无环图(DAG)、边界条件(Corner Cases)。
* ✅ 中文就是中文,英文就是英文。如果是专业库名、函数名或代码关键字(如 `pprof`、`synctest`、`goroutine`、`benchmark`),直接用行内代码块包裹;通用的概念直接用规范中文表达,不搞双语夹杂。

### 2. 绝对不出现"你",坚决杜绝高高在上的说教感
* ❌ 严禁使用"你"、"你们"、"你需要知道"、"你要记住"、"如果你想……"。
* ✅ 作者的定位是一名在一线摸爬滚打、持续学习的工程师(甚至是实习生),绝不当导师或布道者。
* 视角统一采用:
  * **第一人称**:"我最初的直觉是……"、"我们在排查这个问题时发现……"
  * **客观事实陈述**:"这种场景下的常见做法是……"、"测试在这个阶段的核心任务是……"

### 3. 语言必须极其简练大白话,复杂度只留在代码和测试里
* ❌ 严禁堆砌又长又绕的学术黑话和复杂从句(例如:"大模型擅长在严格定界的无状态上下文中完成极限的指令重排与算法降阶")。
* ✅ 高手写博客,话讲得越简单越透彻。能用一句短句讲清楚的,绝不分成两个长句;概念解释用最直接的大白话,深度的证明交给真正的代码实现、火焰图、吞吐量数字和对拍脚本。

## 二、语言去伪存真对照表

| 严禁使用的文风(中二/说教/堆砌黑话) | 顶级大牛推荐写法(简单、平静、克制) | 为什么这样改 |
| :--- | :--- | :--- |
| 御兽流派、开局一个Agent剩下全靠吞 | 让模型在自动化脚本的反馈下迭代 | 告别网梗,用最朴素的话描述自动化工作流 |
| 像看番茄小说一样爽、太香了、神器 | 显著减少了繁琐的人工重复工作 | 不用夸张感叹词,只描述实际效果 |
| 你需要先学会线段树,再去理解它 | 遇到这类区间频繁更新的问题,一般会想到线段树 | 去掉"你",变成客观技术方案介绍 |
| 很多人第一反应是让AI优化,结果AI成了小丑 | 很多时候我们直接把整段代码丢给模型,效果往往很差 | 平视视角,对事不对人,承认真实问题 |
| 大模型在非结构化高维空间中进行启发式试错 | 模型根本不知道程序哪最慢,只能靠猜 | 用一句干净的大白话击中本质 |
| 对拍机制(Stress Testing)是终极杀器 | 找两套代码相互对照测试:一套虽然慢但绝对正确,另一套跑得快 | 解释清楚机制,不带英文后缀,不用夸张修辞 |

---

## 三、行文节奏与排版习惯

1. **短句为主,呼吸感强**:一段推导或代码之后,用一句简短有力的客观陈述收尾。
2. **拿数字和代码说话**:不要泛泛而谈"性能大幅提升",直接贴基准测试数据(如:从 320ms 降至 48ms,内存分配从 14 次降为 0 次)。
3. **坦陈遇到的坑和局限**:真实记录哪些方案行不通、为什么放弃了某种写法。实事求是的记录比完美的虚假结论更有价值。
