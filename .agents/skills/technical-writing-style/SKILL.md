# 极客风格技术博客写作规范

本规范的核心原则是:**语言精练平实,严禁用词浮夸,多用具体数字说话,把复杂度留给代码、基准测试和系统架构**。

---

## 一、写作守则

### 1. 多用具体数字与指标
* 避免模糊形容词:不要写"性能大幅提升"、"耗时很短"、"处理海量数据"、"节省了很多内存"。
* 必须给出真实度量:
  * 延迟与吞吐:例如"P99 延迟从 320ms 降至 18ms"、"单实例吞吐达到 14,000 QPS";
  * 内存与开销:例如"内存分配从 28 allocs/op 优化到 0 allocs/op"、"常驻内存从 1.2GB 压到 85MB";
  * 规模与轮次:例如"跑完 100,000 次随机边界对拍"、"在包含 12 张表、最深 6 层 JOIN 的复杂查询中"。

### 2. 严禁营销号浮夸词汇
* 禁用词库:`绝对`、`超级`、`完美`、`终极`、`秒杀`、`神仙`、`炸裂`、`颠覆`、`无敌`、`天花板`、`彻底`。
* 替换方案:用实测数据和客观事实说话。
  * ❌ "这套方案绝对安全,性能超级强"
  * ✅ "在类型系统的检查下,消除了空指针引用;在连续跑完 10 万次用例时未出现不一致"
  * ❌ "秒杀传统手写逻辑"
  * ✅ "相比手工编写的多重循环,耗时缩短了 76%"

### 3. 不在名词后跟括号英文解释
* ❌ 避免双语括号夹杂:形式化建模(Problem Formalization)、基准(Ground Truth)、对拍(Stress Testing)、有向无环图(DAG)。
* ✅ 中文直接写干净的中文名词;语言关键字、库名、工具名直接用行内代码块包裹(如 `pprof`、`synctest`、`goroutine`、`benchstat`)。

### 4. 禁止出现"你",杜绝说教感
* ❌ 严禁使用"你"、"你们"、"你需要"、"你要注意"。
* ✅ 作者定位是一线实践与记录的工程师,行文视角统一使用:
  * **第一人称探索**:"我最初的直觉是……"、"我们在测试时遇到了一个问题……"
  * **客观技术陈述**:"这类场景通常采用如下方案……"、"验证的核心任务是找出反例……"

### 5. 语言简练透彻,复杂度留给代码
* 解释原理时用最直白精炼的大白话,不堆砌晦涩的学术长句。
* 真正的技术深度体现在:
  * 完整的可运行代码片段与类型定义;
  * 真实的基准测试对比表格;
  * 严谨的架构图与调用链推演。

## 二、极客风格特征清单

要让文章具备纯正的极客与系统工程师质感,行文应自然融入以下要素:

1. **底层的物理感知**:不把程序当黑盒,留意底层机制(如 Linux Page Cache 缓存抖动、Go 编译器的逃逸分析、CPU 缓存行对齐、GC 垃圾回收暂停)。
2. **拿基准测试与工具说话**:习惯性使用 `go test -bench`、`benchstat`、`pprof` 火焰图、`testing.F` 模糊测试工具展示结果。
3. **真实记录失败与局限**:记录哪些尝试失败了、模型在什么边界用例下会产生偏差、方案适用的边界条件是什么。这种真实和严谨正是技术信誉的来源。

## 四、排版与 OINK 极客组件使用规范

遵循"**Native Markdown 优先**"准则,充分借助主题的属性行扩展(`{...}`)提升技术文档的工程美感与可读性:

### 1. 对比选项卡(Tabs)
在进行**新旧技术演进**、**多方案对决**或**标准库 vs 第三方库**对比时,禁止简单垂直堆叠两个冗长的大代码块。使用同组 Tabs 实现就地横向切换,配合 `group` 属性实现全页联动记忆:

````markdown
```go {tab="现代标准库 (Go 1.22+)" group="impl" value="std"}
mux := http.NewServeMux()
mux.HandleFunc("GET /users/{id}", handleUser)
```

```go {tab="旧第三方库 (Gorilla Mux)" value="legacy"}
r := mux.NewRouter()
r.HandleFunc("/users/{id}", handleUser).Methods("GET")
```
````

### 2. 代码块标头与改动高亮(Code Titles & Diffs)
* 生产级代码块必须使用 `{title="path/to/file.go"}` 标明源文件路径,避免裸代码块;
* 依赖瘦身、配置升级、重构前后改动,统一使用 ```` ```diff {title="filename"} ```` 清晰呈现增删行;
* 关键代码行使用 `hl_lines="3-5"` 高亮聚焦。

### 3. 原生架构目录树(FileTree)
严禁手写容易在移动端折行错位的 ASCII 字符(`├──`、`└──`)。涉及模块分层、工程结构与生成产物拓扑时,统一使用 ```` ```filetree ````:

````filetree
- internal/
  - handler/         # HTTP 请求入口与路由
  - service/         # 纯业务逻辑编排
  - repository/      # 数据持久化代码
- go.mod             # 零间接依赖清单
````
利用主题提供的目录折叠、专属文件类型图标与右侧像素级自动对齐的注释列。

### 4. 流程步骤条(Steps)
在描述工具链配置、环境搭建、CI/CD 质量门禁流转等具有严格时序的操作时,在有序列表末尾紧跟 `{.steps}`:

```markdown
1. 编写原生 `schema.sql` 与 `queries.sql`
1. 配置 `sqlc.yaml` 开启编译期类型推导
1. 执行 `sqlc generate` 自动生成持久层代码
{.steps}
```
纯 CSS 渲染出带有纵向连接线与数字节点的流水线样式。

### 5. 章节总览(_index.md)写作准则:阐述工程大义,严禁枚举文章
主题已配置 `section_index: cards`,会自动读取下级文章的 `title` 与 `description` 生成底部的卡片导航,因此 **`_index.md` 严禁手动罗列文章链接列表**(避免生成重复的冗余卡片)。

`_index.md` 的核心职责是**用深度的工程思辨阐述本章的大义与哲学**:
* 重点剖析**为什么在人机协同 / AI 时代必须这么做**(例如解释代码基座平整性、上下文窗口消耗、隐式魔法导致模型推理发散等系统级原因);
* 梳理生产演进中的真实矛盾与工程痛点,为读者和模型建立统一的先验心智模型;
* 把具体的微观实现、对比实验与基准测试留给下属各节展开。

> `{.cards}` 仅在正文内偶尔需要横向聚合外部异构工具或跨专栏独立资源时按需使用,不得用于章节索引页枚举子章节。

### 6. 参数与字段卡片(Fields)
记录配置项、命令行 Flag、结构体参数字典时,在表格末尾附加 `{.fields meta="类型 默认值"}`,防止在移动端或窄屏侧边栏产生不可阅读的横向滚动溢出。

### 7. 硬核原理解析块(Callouts)
在阐述底层硬件指令集(如 AES-NI、AVX2、POPCNT)、操作系统内核零拷贝旁路(sendfile/splice)或生产高危陷阱时,使用 GFM 原生警告块:
```markdown
> [!TIP] 硬件指令加速机理
> 在 amd64 架构下,maphash 汇编直接发射 AESENC 单轮加密硬件指令,由处理器内部硬件单元流水线化执行雪崩混淆。
```
* **标题规范**:自定义标题直接跟在 `> [!TIP] 标题内容` 同一行,OINK 会自动将其作为专属卡片标头,避免生成默认的"提示"并与正文挤在同段;
* **符号规范**:映射与推导箭头统一使用原生 Unicode 字符 `→`,严禁在非数学公式段落中使用 `$\rightarrow$`,保证在 GitHub、终端与所有主题渲染器下的通用纯净显示。

### 8. 版本与状态标识(Badge)
在特性引入版本、废弃状态、环境要求处,规范嵌入轻量徽标:
`{{< badge text="Go 1.22+" tone="success" >}}` 或 `{{< badge text="已归档" tone="danger" >}}`。
